# NOCIX 双阶段登录设计规格

## 目标

支持 NOCIX 已有账户的真实登录流程：第一次提交账号和密码，进入新的登录页面后再次提交账号和密码，
然后等待邮箱验证码。验证码由用户在面板中手动输入，登录成功后继续购物车、PayPal 和自动下单流程。

## 流程

```text
库存恢复
  -> 打开购物车
  -> 第一次登录：账号 + 密码
  -> 第二次登录：账号 + 密码
  -> 邮箱验证码页面
  -> waiting_for_email_code
  -> 用户从邮箱读取并在面板提交验证码
  -> 验证码提交成功
  -> 继续系统选择、价格校验、客户确认、PayPal 和下单
```

如果 NOCIX 页面在某次流程中不要求验证码，worker 直接继续，不强制等待。

## 凭据和验证码安全

- NOCIX 密码继续使用现有 Fernet 加密存储。
- 两次登录都使用同一份解密后的账号和密码，但只在 worker 内存中使用。
- 邮箱验证码只存在内存事件/队列中，不写入 SQLite、日志、Telegram、浏览器 URL 或前端存储。
- API 只接受验证码，不返回验证码，也不在错误信息中回显验证码。
- 任务停止、取消、失败、成功和超时都会清除内存中的验证码和等待事件。

## Worker 生命周期

新增状态：

```text
login_first
login_second
waiting_for_email_code
```

worker 在验证码页面保持当前 Selenium session，不退出、不重新创建浏览器。
等待期间不执行库存轮询或下单动作。验证码提交事件唤醒同一个 worker，worker 填入验证码并继续。

验证码错误时：

- 保持 `waiting_for_email_code`；
- 清除本次验证码值；
- 返回安全的错误提示；
- 允许用户重新提交。

验证码超时、取消或浏览器失效时：

- 任务进入普通 `failed`；
- 不创建订单失败记录，因为尚未进入订单提交阶段；
- 发送不包含验证码或密码的 Telegram 通知。

## API

```text
GET  /api/tasks/{id}/login-state
POST /api/tasks/{id}/email-code
POST /api/tasks/{id}/login-cancel
```

提交请求：

```json
{"code":"123456"}
```

响应只返回状态和安全提示：

```json
{"status":"ordering","message":"verification accepted"}
```

所有接口需要 `X-API-Key`。未知任务返回 404，任务不在验证码等待状态返回 409，验证码格式错误返回 422。

## 页面识别

Selenium 使用稳定的字段优先级查找账号、密码和验证码元素，并通过页面 URL/可见字段判断阶段。
找不到登录字段时抛出明确错误，不会盲目点击下单按钮。

实现必须支持测试注入页面选择器，不能在单元测试中访问真实 NOCIX 或邮箱。

## 前端

任务卡在 `waiting_for_email_code` 状态显示：

- 等待邮箱验证码；
- 验证码输入框；
- 提交验证码；
- 取消登录；
- 安全错误提示；
- 等待时间或超时提示。

面板支持简体中文和 English，默认简体中文。验证码输入框使用密码/一次性代码输入语义，
不保存到 localStorage/sessionStorage，提交成功或失败后立即清空。

## 测试

- 两次登录分别填写账号和密码。
- 第二次登录发现验证码页面后进入等待状态并保留浏览器 session。
- API 提交验证码唤醒同一 worker。
- 正确验证码继续下单，错误验证码可重新输入。
- 验证码超时、取消、停止和浏览器异常会清除内存验证码。
- 验证码不会出现在数据库、日志、Telegram、API 响应或前端存储。
- 未出现验证码页面时直接继续。
- 任务状态、订单统计、代理、PayPal、Telegram、双语界面和现有生命周期测试继续通过。
